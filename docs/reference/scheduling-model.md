# thyme scheduling model contract

This document is the **contract** for thyme's scheduling model: what is
guaranteed, what is deliberately not provided, and how to reason about
configuration. See [ADR 0003](../design/adr/0003-no-callback-group-executor.md)
for the decision record.

- Scope: `CyclicThread` / `EventThread` in `thyme::runtime`, and the threads and
  placement generated by `gen_graph` from `graph.yaml`.
- The overall execution model (cyclic / event / transport semantics) is in
  [ARCHITECTURE.md](../../ARCHITECTURE.md) §5. This document defines only the
  **scheduling contract**.

## 1. Core contract

1. **By default one node = one thread; with sharding one shard = one thread.**
   `gen_graph` generates one `CyclicThread` (`exec: cyclic`, default) or
   `EventThread` (`exec: event`) per node. The exception is an event sink with
   `threads: N`, which expands into N physical workers. Wiring is fixed at
   compile time by `graph.yaml`; threads are never added or removed at runtime.

2. **Callbacks run serially on their thread (and therefore their shard).**
   - cyclic node: `OnLoop()` once per period;
   - event node: `EventThread` waits in `WaitAny` on the wake hub, drains the
     batch, and calls each input edge's `On<Channel>(const T&)` in order.
   - All callbacks of one physical worker run on the same thread and **never
     concurrently**; application member state on that worker needs no lock.
     Different shards have independent objects and threads and may run
     concurrently, so a logical node is no longer a single mutual-exclusion
     domain. Generated `Loop()` / `Dispatch()` are `final`; replay pause and
     recording mirror taps are built into the framework.

3. **No executor, no callback group.** thyme does not implement ROS 2-style
   executors or callback groups; **the thread itself is the mutual-exclusion
   group**. Callbacks are generated at compile time and bound to fixed threads,
   so there is no "dynamically registered callbacks sharing an executor queue"
   problem.

4. **Concurrency = more nodes or threads.** For parallel processing, split
   nodes (one thread and placement each). If one event sink needs several
   independent inputs to run concurrently, use **static input sharding**
   (`threads: N`), not a general executor. The first version supports only
   event sinks with no output edges and at least N input edges; cyclic nodes,
   non-sinks, no-input nodes, `N > input edges`, `N=0/N>64`, and physical-name
   collisions are rejected at generation time. Local input edges are numbered
   in YAML order and edge `ordinal` goes only to shard `ordinal % N`; each
   message is consumed once. Each `<id>__s<i>` has its own object, EventThread,
   health slot, placement, overrun handling, perf, and `input_budget` sized to
   its local inputs. Shards are serial internally and concurrent with each
   other; there is no cross-shard ordering, join, or atomic batch across inputs.
   MP queue data SHM is initialized once; wake words are sharded as
   `_wk_<id>__s<i>`. Record/replay still operate once per logical channel.
   Admission conservatively replicates hz/WCET per physical worker and does not
   multiply capacity by N. **Shards do not share `this`, but application-owned
   static/global state is still shared and must be made thread-safe by the
   application.** Extra ctor resources for known types cannot be shared
   silently: the first version rejects sharded nodes with ctor resources other
   than `{health}`.

5. **The DAG exists only at compile time.** The graph is used for wiring, rate
   derivation (`--explain-rates`), and admission analysis
   (`--explain-sched`); **there is no runtime DAG executor**. Feedback edges
   must be explicit `feedback: true` plus a delay.

## 2. ThreadPlacement: fields, defaults, and generation path

Scheduling configuration is per **thread (= node)**, declared through
`graph.yaml` node fields. `gen_graph` emits `thyme::ThreadPlacement`
(`include/thyme/runtime/cyclic_thread.h`), and `ApplyThreadPlacement`
(`include/thyme/runtime/placement.h`) applies it after thread creation.
`CyclicThread` and `EventThread` share the same contract.

| `graph.yaml` field | `ThreadPlacement` member | Values | Default |
|---|---|---|---|
| `cpu_set` | `cpus[]` / `ncpus` | CPU id list (≤ `kMaxCpus` = 64; larger rejected during validation) | Empty = no affinity |
| `sched_policy` | `policy` | `fifo` / `rr` / `other` | Unset (see below) |
| `priority` | `priority` | Integer `1..89` (explicit); cyclic nodes use RM when unset, event nodes default to 10 | RM / 10 |
| `placement_fail` | `fail` | `best_effort` / `require` | `best_effort` |
| `deadline_ns` (event only) | `EventThread` constructor argument | Dispatch budget in ns | 0 = unchecked |
| `overrun` | `SetOverrunPolicy` | `skip` / `degrade` / `restart` | `skip` (event nodes require `deadline_ns > 0`) |
| `input_budget` (event only) | `SetInputBudget` | Maximum messages per input per Dispatch (>0) | 0 = unlimited |
| `phase_mode` (graph-level) | `phase_mode` / `phase_ns` | `off` / `best_effort` / `require` | `off` (first wake is still `now + period`) |

Behaviour details (code is authoritative):

- **When `sched_policy` is unset** (`Policy::Unset`): on Linux, best-effort
  attempts `SCHED_FIFO` with `ThreadPlacement::priority` (default 10). Failure
  (for example `EPERM` without permission) is silently ignored. This is not a
  real-time guarantee; it is only "try".
- **When `sched_policy` is explicit:** calls `pthread_setschedparam` with
  `fifo`/`rr`/`other`. With `placement_fail: require`, an affinity or sched
  failure fails `Start()` and tears down the thread; with `best_effort`, the
  failure is ignored.
- Generated code: `tools/gen/gen_graph/emit_ports.cpp` (node placement section);
  YAML parsing/validation: `tools/gen/gen_graph/yaml.cpp`.
- An event node's `hz` means steady-state **messages/s**, not a period;
  `deadline_ns` is an optional Dispatch budget (see §4).

### Automatic RM priorities

`gen_graph` assigns rate-monotonic (RM) priorities to cyclic nodes without an
explicit priority: shorter period (higher `hz`) gets higher priority.

| Item | Rule |
|---|---|
| RT priority range | `1..99` (Linux `SCHED_FIFO`/`SCHED_RR` semantics) |
| Graph/RM range | `1..89` |
| System-reserved range | `90..99` (system/watchdog/external RT threads; the graph must not use it) |
| Default priority | `10` (matches `ThreadPlacement`) |
| RM value | Rank of distinct declared periods in ascending order: fastest rate `89`, next `88`, …; equal periods share a priority; beyond 89 distinct periods clamp to `1` |
| Explicit `priority` | **Explicit wins**, but must be `1..89` (`0`, `>99`, and the reserved range are validation errors) |
| No period (`exec: event`) | `hz` is messages/s, not a period, so **RM is not guessed**. `--sched-priority=best-effort` (default) keeps 10 and emits `SCHED_WARN`; `strict` fails generation (exit 2) |

- Nodes with explicit priority do not participate in RM ranking and do not
  consume a rank slot; RM keeps "shorter period, higher priority" among the
  remaining cyclic nodes.
- A cyclic node without `priority` always receives an RM value; results are
  written to `generated/sched_plan.h` (`kGraphSchedPlan`, including
  `period_ns`/`priority`/`priority_source`/`core`/`phase_ns`) and into
  `ThreadPlacement` (`scheduling_apply.inc` / `wiring.cpp`).
- The best-effort FIFO path for `Policy::Unset` now uses the `priority` field
  (previously hardcoded to 10). It remains best-effort without
  `CAP_SYS_NICE` and takes effect with permission. For a hard guarantee, set
  `sched_policy: fifo` + `placement_fail: require`.
- `sched_plan.h` uses `static_assert` to lock `SchedPlanRow` layout (48 B,
  32/64-bit consistent), the priority range, the reserved range, and
  `kGraphSchedPlanCount > 0`.

### Static phase/offset (default off)

`--explain-sched` already computes each node's `phase_ns` /
`phase_in_period_ns`. The graph-level `phase_mode` connects it to the cyclic
thread's **first wakeup**:

- **`off` (default):** no `ThreadPlacement::phase_*`; `CyclicThread` still
  starts at `now + period`. Committed cyclic golden bytes are unchanged.
- **`best_effort`:** writes `phase_ns = phase_in_period_ns` only for
  `exec: cyclic` nodes with `phase_complete`; incomplete phases emit
  `SCHED_WARN` and keep offset 0. `exec: event` is ignored.
- **`require`:** any cyclic node with `phase_complete=false` fails generation
  (exit 2) without writing a tree.

The first deadline is `AlignCyclicDeadline(epoch, phase_ns, period, now)`:
`epoch + (phase_ns mod period)`. A late-starting thread delays by whole periods
instead of catching up. All cyclic threads in one process share the
`CLOCK_MONOTONIC` epoch published by the first `Start()`; hand-written code may
override `ThreadPlacement::start_epoch_ns`. Cross-process alignment is not
provided (not a hard real-time guarantee). Admission's `Σ WCET/period` is
unchanged; phase is not kernel affinity/policy and is not compared by
`SchedMismatchMask`. **Non-goals:** runtime DAG executor, dynamic phase changes.

### Admission analysis and `--explain-sched`

`gen_graph --explain-sched` performs **compile-time DAG analysis only**, adds no
runtime DAG executor, and writes no files:

- **stdout:** byte-stable JSON (`thyme.gen_graph.sched.v1`) containing
  - `policy`: priority range, reserved range, defaults, `priority_mode`,
    `admission_mode`, thresholds, `admission_status`;
  - `topological_order`: Kahn topological sort over non-feedback edges;
  - `nodes`: per node `exec`, `hz`, nominal `period_ns` (event nodes marked
    `period_basis: hz_message_rate`), `rm_eligible`, `wcet_ns`/`wcet_known`,
    `priority`/`priority_source`, `core`,
    `phase_ns`/`phase_in_period_ns`/`phase_complete`, `in_feedback_loop`;
  - `feedback_edges`: `from`/`to`/`channel`/`delay_ns`/`loop_nodes`;
  - `cycles`: `rejected` and `feedback_loop_nodes` (unmarked cycles are already
    rejected during validation and never reach the report);
  - `cores`: per-core `Σ C_i/T_i`, `status` (`analyzed` / `partial` /
    `not_analyzed`), `overloaded`, `above_warn`, `nodes`, `unknown_nodes`;
  - `chains`: each sink's critical path, `end_to_end_ns`,
    `completion_ns = phase + WCET`, `deadline_ns`, `slack_ns` (`null` when cost
    or period is unknown);
  - `notes` / `warnings` / `errors`.
- **stderr:** a human-readable table of the same plan (topological order, node
  rows, per-core utilization, chain slack, feedback annotations, admission
  verdict).
- **phase/offset:** a source node is 0; every other node uses
  `max(pred.phase_ns + pred.WCET)` (feedback edges cut). If any predecessor's
  WCET is unknown, `phase_complete=false` and phase is a lower bound rather than
  an invented value.
- **Cost source:** `wcet_ns` (a `graph.yaml` field, > 0) is the only source;
  there is no automatic injection of measured values. Undeclared means unknown
  (`wcet_ns=0`, `wcet_known=false`) and is **never treated as zero cost**.
  For event nodes `hz` is messages/s; admission treats it as the average
  inter-arrival interval for `C_i/T_i` (marked `hz_message_rate`) and does not
  model bursts.
- **Core assignment:** the first CPU in `cpu_set`; a node without `cpu_set` is
  `core: null` (unassigned) and **does not participate in admission** (without
  a core, overload cannot be asserted). Multiple CPUs emit `SCHED_WARN` and
  count against the first.
- **Admission thresholds** (`--sched-admission=`):

  | Mode | `Σ C_i/T_i > 0.9` | `> 1.0` |
  |---|---|---|
  | `error` (default) | `SCHED_WARN` (headroom) | `SCHED_ERROR`, exit 2, no tree |
  | `warn` | `SCHED_WARN` | `SCHED_WARN`, exit 0 |
  | `off` | unchecked | unchecked |

  Only cores with all costs known report `analyzed`; partial knowledge is
  `partial`, no knowledge is `not_analyzed`, both stated explicitly rather than
  silently passing.
- **Chain slack:** each sink's critical path uses
  `min(period, event deadline_ns)` as its deadline, and
  `slack = deadline - (phase + WCET)`. Unknown WCET gives `slack_ns=null`.
  Negative slack appears in the human output and does not fail by itself
  (acceptability depends on deadline/overrun policy).
- Code generation reuses the same plan: in `error` mode, overload fails before
  emit; `--check` uses the same plan, so priority/table drift is detected.

### Capacity admission

Capacity uses the same `SchedPlan` and report as `Σ WCET/period`; JSON
`capacities` gives per-edge input, requirement, suggested capacity, and status,
and `policy.capacity_status` gives the aggregate. Normal generation and
`--check` run this validation too, not only explicit explain mode.

- `lossless` defaults to `false`, so old graphs keep latest/overwrite semantics
  and generated output. `lossless: true` applies only to `notify` / `queue` /
  `broadcast`; `latest` has no per-frame lossless semantics and is rejected.
  Effective capacity is the edge-level `depth`, or `ring_cap` when unset.
- Without an explicit `max_lag_ms`, the consumer's worst-case lag is
  `consumer_period + deadline_ns` (when the event deadline is configured),
  otherwise `consumer_period + wcet_ns`. The requirement is
  `required_slots = ceil(producer_hz × lag_ns / 1e9)`. `max_lag_ms` is an
  explicit override and is allowed only with `lossless: true`.
- BF-07 edges declare `before_ms`, `after_ms`, and `per_frame_write_ms` (all
  three together) plus optional `pin_budget`. The shared formula computes
  `required_slots = ceil((before + after + per_frame_write) × rate) + pin_budget`,
  where `pin_budget` reserves slots for other concurrent readers. The report
  keeps the BF-07 window lag and pin budget so unknown is never treated as a
  zero budget.
- Both calculations use the same integer round-up implementation in
  `tools/gen/gen_graph/capacity.h` and check addition, multiplication, and
  power-of-two suggestion overflow. Do not write a second formula.
- Insufficient capacity reports `required_slots` and the power-of-two
  `suggested_capacity`. Default `--sched-capacity=error` returns exit 2 without
  generating a tree; `best_effort` downgrades to `SCHED_WARN` and marks each
  result and the aggregate `best_effort`, explicitly accepting unverified frame
  loss rather than claiming lossless delivery. It is independent of
  `--sched-admission=warn|off`; the latter does not relax capacity gates.
- When WCET needed for lag derivation is undeclared, rate/lag is invalid, or
  arithmetic overflows, status is `partial` — never continued as 0. It fails by
  default too; only explicit `best_effort` may continue in an "unverified"
  state. `max_lag_ms` can remove the WCET dependency. A graph with no declared
  lossless/BF-07 capacity is `capacity_status=not_analyzed` and does not fail.

### SCHED_DEADLINE evaluation

`SCHED_DEADLINE` is not enabled; FIFO+RM continues. An event node's
`deadline_ns` remains a Dispatch overrun budget and cannot be mapped to a CBS
period; declared `wcet_ns` is not a validated kernel runtime reservation. Only
hard cyclic nodes with complete three-parameter semantics, a provable
system-level admission, CPU/I/O protection for other threads, and target-board
comparison may justify re-evaluating a separate placement backend. See
[ADR 0011](../design/adr/0011-sched-deadline-evaluation.md).

## 3. Accepted limitations

These are part of the model, not bugs:

- **No dynamic load balancing or work stealing.** A slow callback blocks other
  callbacks on the same thread; the framework never migrates work.
- **Mixed-rate inputs on one `EventThread` can starve each other.** There is no
  per-channel priority; inputs in one wake batch are processed serially in drain
  order, so a slow low-frequency callback delays a high-frequency one. **Split
  the node first**; if that is impossible, use `input_budget`.
- **Event nodes have no RM priority.** `hz` is messages/s, not a period, and
  `gen_graph` does not guess; write `priority` explicitly (or accept default 10
  plus `SCHED_WARN`). `--sched-priority=strict` turns "no period and no explicit
  priority" into a generation error.
- **Overrun policy is node-level and bounded:** `degrade` halves the rate at
  most; `restart` only calls the application hook and does not clear queues for
  the application (see §4).
- **No callback-level deadline or budget.** Admission is per thread (node):
  `Σ WCET/period` per core, with cost from `wcet_ns`; undeclared means
  `not_analyzed`.
- **The DAG exists only at compile time.** Unmarked cycles are rejected;
  `feedback: true` plus a delay is annotated and cut in the report. There is no
  runtime DAG scheduler.

## 4. Overrun: counting plus skip / degrade / restart

**Detection:** with `deadline_ns` configured, an event node's `Dispatch()`
exceeding its budget is one deadline miss; a cyclic node's `Loop()` exceeding
its period is one miss (the period is its deadline). Each miss still calls
`HealthSlot::MarkDeadlineMiss()` once and assigns **one** cause counter
(long-callback / queue-backlog / os-preemption; their sum equals
`deadline_miss_cnt`). These are independent of policy counters: one miss = one
cause + one policy action, never a double-counted health miss.

**Policy** (`graph.yaml` `overrun`, or `SetOverrunPolicy()` at runtime):

| Policy | cyclic | event | Semantics/risk |
|---|---|---|---|
| `skip` (default) | Keep the period (including spiral-of-death snap) | Keep draining | Observability only; recovery happens naturally |
| `degrade` | Period ×2; recover after `kDegradeRecoverCycles=8` on-time periods | Insert a cooldown equal to `deadline_ns` before each batch; recover after 8 on-time batches | Rate is halved at most; **never** degrades indefinitely on consecutive misses; the recovery window is a hardcoded constant |
| `restart` | Call `OnOverrunRestart()`, `next = completion + period` | Call `OnOverrunRestart()`, keep draining | The framework **does not clear** input rings or reset application state; the hook runs on the RT thread and must be non-blocking and zero-allocation; queued old data is still processed |

**Counter outputs:**

- Per-policy action counters: `overrun_skip_actions()` /
  `overrun_degrade_actions()` / `overrun_restart_actions()`
  (`CyclicThread` / `EventThread`).
- In-process session marker: `thyme::overrun_session::count()` /
  `last_policy()`, updated once per miss (not on the hot path). A cross-process
  package marker is future work: it needs shared-memory counters (an ABI
  change), so no package flag is written today.
- `degrade` state is readable: `degraded()`,
  `CyclicThread::effective_period_ns()`.

**Relationship to supervisor restart:** supervisor restart is **process-level**
(backoff, budget, health-slot reset). `restart` here is **node-level
re-arming**, not a process restart; a process that truly exits or stalls is
still handled by the supervisor. The two never double-count one failure.

## 5. Scheduling observability

Placement is **best-effort** (§2): requesting `fifo` without `CAP_SYS_NICE`
makes `pthread_setschedparam` fail with `EPERM`, and the thread silently stays
in `SCHED_OTHER`. "Requested" is not "granted", so observability has four parts:

1. **Actual scheduling state and mismatch detection**
   (`include/thyme/runtime/sched_state.h`). After placement, `CyclicThread` /
   `EventThread` read the **actual** policy/priority/affinity once in `Start()`
   with `pthread_getschedparam` / `pthread_getaffinity_np` (cheap, startup-only)
   and store `actual_sched()`. `sched_mismatch()` compares item by item against
   the request (`SchedMismatchMask`: policy / priority / affinity):
   - `Policy::Unset` is a contractual best-effort attempt; ending up with
     `OTHER` is expected and **not** reported as a mismatch;
   - `SCHED_OTHER` priority is always 0 in the kernel and is not compared;
   - affinity is compared only when `cpu_set` was explicit.
   A nonzero mismatch emits a stderr warning and
   `HealthSlot::MarkSchedMismatch()` (in-process count). The count aggregates
   through `SharedHealthPage` into the status server's per-role
   `health.sched_mismatches` JSON. Per-thread actual policy/priority/affinity
   are available through `actual_sched()`.
2. **Per-callback work** (`EventThread::NoteCallbackWork`). Dispatch batch work
   is already recorded (perf type 3 plus a work histogram); this adds
   **edge-level** callback duration. Generated/hand-written Dispatch wraps each
   input callback with `NowNs()` and calls
   `NoteCallbackWork(edge, dur)` using the edge's `RecordStructId`; samples go
   into a separate `cb_work()` `PerfSampler`, flushed as per-edge sample (type 1)
   and percentile (type 2) blocks plus an aggregate histogram block (type 6,
   series 2), kept separate from latency samples so percentiles do not mix.
3. **Queue depth** (`Waitable::Depth` plus the probe registry).
   `Waitable` exposes advisory `Depth()` (instantaneous pending count; SPSC
   snapshots may be off by one). Implemented for `NotifPipe` (ready-ring
   backlog), `ShmSpscRing` (shm ring fill, head-tail), and `SpscRing`.
   `EventThread::RegisterObservability` registers a queue-depth probe on
   `ProcSampler` for each input that reports Depth (series id ≥ 16,
   instantaneous), and the sampling thread writes perf type 5. The registering
   side has zero hot-path code.
4. **Overrun cause classification** (`include/thyme/runtime/overrun.h`).
   A deadline miss is still just counted (policy is separate), but each miss is
   assigned one **primary cause**, with the three summing to
   `deadline_miss_cnt`:
   - `overrun_long_callback_count`: the callback itself overran (fallback);
   - `overrun_queue_backlog_count`: inputs still have backlog when an
     over-budget batch ends;
   - `overrun_os_preemption_count`: wake-to-callback start latency exceeds half
     the budget. This is a **lower bound**: preemption inside Dispatch/Loop and
     genuinely long work cannot be distinguished without `/proc` on the hot
     path, so those count as long-callback. Cyclic threads use wake error as
     dispatch latency in the same classification.
   The three counters can also be registered as type-5 counter series through
   `RegisterObservability`.

Observability outputs: perf type 1/2 (per-edge latency and per-callback work),
type 3 (batch work), type 5 (process counters, queue-depth probes, overrun cause
counters), type 6 (fixed-bucket histograms: node/edge latency and per-callback
work p50/p90/p99/p999 plus exact max, 1,332 B per series, mergeable across
processes by bucket addition with `thyme_log_merge --hist`); status server adds
`sched_mismatches` to each role's `health`.

## 6. Do not configure thyme with callback-group thinking

ROS 2 thinking is "register callbacks with an executor and use callback groups
to control exclusion/concurrency". There is no counterpart in thyme, and
copying the model misconfigures it:

| Scenario | Do not (callback-group thinking) | Do (thyme thinking) |
|---|---|---|
| Two inputs at different rates | Put them in one node and expect group scheduling | Split into two nodes, each with its own thread and placement (preferred) |
| Shared state within a shard | Add a mutex against "concurrent callbacks" | No lock needed — same-shard callbacks are serial; cross-shard/static state still needs synchronization |
| Raise one callback's priority | Look for a "callback priority" setting | It does not exist; priority is per thread, configured with `sched_policy`/`priority` on the node thread |
| More parallelism | Wait for executor load balancing | Split nodes / add threads; for an event sink with multiple inputs use `threads: N` static sharding |
| Real-time guarantee | Rely on default priority 10 | The default is best-effort and fails silently; real-time threads need explicit `sched_policy: fifo` + `priority` + `placement_fail: require` |
| Slow callback | Expect preemption/migration | It will not happen; reduce work, split the node, or accept blocking and observe `deadline_ns` counters |

In one sentence: **in thyme, the scheduling unit is the thread and the
configuration unit is the node; to change scheduling behaviour, change the
graph, not a runtime scheduler.**

## 7. Example: 10 Hz and 100 Hz inputs on one EventThread

An `exec: event` node has two inputs:

- input A at 10 Hz (for example perception), `On<A>` takes about 40 ms;
- input B at 100 Hz (for example chassis state), `On<B>` takes about 0.5 ms.

**What goes wrong:** when the EventThread wakes, it drains the batch and
dispatches serially. One A frame makes `On<A>` occupy the thread for about
40 ms; roughly four B frames arriving meanwhile wait in the queue, producing a
~40 ms latency spike for B. With `deadline_ns` configured, that Dispatch counts
one deadline miss. If B's input queue `depth` is insufficient, B is lost or
overwritten according to delivery semantics. This is not scheduler unfairness:
the model never promised fairness among inputs on one thread.

**Supported mitigations, in priority order:**

1. **Split the node (preferred):** separate nodes for A and B, each with its own
   thread; give B a higher `priority` (or isolate CPUs with `cpu_set`).
2. **Per-input budget: when splitting is impossible, set
   `input_budget: N` on the event node (or `SetInputBudget(N, input_count)` at
   runtime). Generated `Dispatch()` calls `InputBudgetAvailable(i)` /
   `ConsumeInputBudget(i)` in each in-edge drain loop, processing at most N
   messages per input per batch; B frames no longer wait behind A's entire
   40 ms queue. Each batch that hits the cap is counted per input
   (`input_budget_exhausted_count(i)`) and can be registered as a perf type-5
   counter. Default 0 = unlimited; the hot path adds only one predictable
   branch.
3. **Static input sharding:** an event sink declares `threads: N`; input edges
   are statically split across N independent workers at compile time (the first
   version allows no output edges). Callbacks within a shard remain serial;
   different shards may run concurrently. This is not a general callback group.
4. **Shorten the slow callback:** move `On<A>`'s heavy work to a downstream node
   (publish an intermediate result) or reduce copies so 40 ms fits B's queueing
   budget.

**Unavailable:** per-channel priority, callback-group exclusion/parallel
configuration, executor load balancing, or runtime preemption of B.

`gen_graph --explain-rates` and normal generation print
`SCH03_WARN ... split the node (preferred) or set input_budget` for an event
node with inputs differing by ≥ 2× and at least two inputs. It is a
**suggestion**, not a rejection: splitting requires a graph change, while a
budget is the fallback within the node.
