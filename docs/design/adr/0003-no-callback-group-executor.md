# ADR 0003: no callback group / executor

- Status: Accepted (formal record of the scheduling decision)
- Date: 2026-10-23
- Scope: scheduling model — `CyclicThread` / `EventThread`, and the threads and placement generated by `gen_graph`

## Context

ROS 2 callback groups and executors solve a specific problem: concurrency and
mutual exclusion when **dynamically registered callbacks share an executor
queue**. A `MutuallyExclusive` group guarantees that callbacks in the group do
not run concurrently; a `Reentrant` group allows concurrency; a single- or
multi-threaded executor decides how many callbacks are taken from the ready
queue in parallel.

thyme's problem has a different shape:

- callbacks (`OnLoop` / `On<Channel>`) are **generated at compile time** and
  bound to a fixed node and a fixed thread; there is no runtime registration and
  no shared ready queue;
- by default one node = one thread. With static sharding, one shard = one
  thread and callbacks in a shard run serially — **the thread itself is the
  mutual-exclusion group**, so `MutuallyExclusive` semantics fall out of the
  thread boundary;
- concurrency is expressed by splitting nodes or adding threads. Placement
  (affinity, `SCHED_FIFO/RR/OTHER`, priority) is configured statically per
  thread.

Introducing an executor would move "which callback runs when, on which thread"
from compile-time visibility to runtime scheduling decisions, destroying
determinism and WCET analyzability. That is a core thyme trade-off relative to
ROS 2/DDS and must not be traded away for convenience.

## Decision

1. **No ROS 2-style callback groups or executors.** thyme provides no executor
   abstraction, no callback-group semantics, and no runtime callback
   registration.
2. **Static thread model:** by default one node = one thread; callbacks run
   serially on their thread; concurrency = more nodes or threads; a thread is
   its own mutual-exclusion group.
3. **The escape hatch is static input sharding, not a general executor.** When
   one event sink needs several independent inputs to run concurrently, use
   `threads: N` at compile time to split local input edges into N independent
   workers by `ordinal % N`. Callbacks within a shard remain serial; different
   shards may run concurrently. There is no shared executor, cross-shard
   ordering, or join.
4. **The DAG exists only at compile time** (wiring, rates, `--explain-sched`).
   There is no runtime DAG executor. Feedback must be explicit:
   `feedback: true` plus a delay.
5. **Future rule:** if stronger scheduling capability is genuinely needed,
   **do static sharding first** (`threads: N` plus input sharding), and only
   discuss an executor after proving it insufficient. Introducing an executor
   requires a new ADR that explains how WCET analyzability is preserved.

## Alternatives

- **A. ROS 2-style single/multi-threaded executor plus callback groups:**
  familiar and expressive, but moves scheduling decisions to runtime, breaking
  determinism and WCET analyzability. It also solves a problem thyme does not
  have (dynamic registration plus a shared queue). Rejected.
- **B. Work-stealing executor:** improves load balancing but introduces runtime
  scheduling and unpredictable migration/preemption points; conflicts with
  static placement (cpu_set, RM priorities). Rejected.
- **C. `SCHED_DEADLINE` plus runtime admission:** hands scheduling to the kernel
  CBS. Considered only for hard cyclic nodes with provable admission; it is a
  placement-layer supplement, not a callback scheduler, and does not change this
  decision. Evaluation and mandatory gates are in
  [ADR 0011](0011-sched-deadline-evaluation.md); currently disabled.
- **D. This proposal: static threads plus static input sharding as the escape
  hatch:** keeps everything visible and analyzable per thread; the cost is no
  dynamic load balancing. Accepted.

## Consequences

- **Benefits:** scheduling behavior is fully determined by the graph. Each
  thread's WCET, priority, and affinity can be statically analyzed and audited
  (with admission analysis and `--explain-sched`). There is no runtime scheduler
  overhead or surprise.
- **Costs (explicitly accepted):** no dynamic load balancing or work stealing;
  a slow callback blocks other callbacks on the same thread; mixed-rate inputs
  on one `EventThread` can starve each other. These limits and mitigations are
  documented in
  [docs/reference/scheduling-model.md](../../reference/scheduling-model.md).
- **Constraint on configurers:** do not configure thyme with callback-group
  thinking. The scheduling unit is the thread; the configuration unit is the
  node. Changing scheduling behavior means changing the graph.
